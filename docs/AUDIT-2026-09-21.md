# tellodb — parallel audit, 2026-09-21

Eight parallel read-only audits. Four completed (retrieval correctness, storage
correctness, instrumentation, paper readiness); four were killed by a session
rate limit before reporting (shrink, speed, durability, distribution) and must
be re-run.

Goal this audit serves: "SQLite for AI agents" — batteries-included, minimal,
fast, zero-config, embeddable, with a systems paper at the end.

written before today cited `benchmarks/BASELINE.md` (graph 138–164 ms of a
~200 ms query, ~70%). That file is a **smoke tier, n=10, RUNS=1, commit
`878a2b5f` marked dirty** — three phases stale. The current dev run
(`benchmarks/runs/20260919_143617_dev/`, LongMemEval, n=149) says:

| rerank | 54.0 | 193 | 23.0% |
| planning | 38.5 | 138 | 16.4% |
| session | 36.5 | 75 | 15.6% |
| **graph** | **31.7** | 53 | **13.5%** |
| hydrate_obs | 31.0 | 67 | 13.2% |

| **engine_total** | **234.5** | **579** | |

Graph is fifth. `route + rerank + planning = 152 ms`. The budget is flat, so
there is no single lane to delete. Also: `no_graph` is already measured as
significant-and-nearly-free (LongMemEval −2.7 recall_any (−5.4…−0.7) for −5.7%

Action: regenerate `BASELINE.md` at dev tier; update RESEARCH_PLAN §2/A2, §9.2,

**C2. The cosine-fallback mechanism was wrong; the inversion is real via a
different route.** `src/query/score.rs:133` falls back to cosine when
`base_score <= 0.001` — but `get_observations_batch` returns
`embedding: Vec::new()` unconditionally (`src/storage/repo/memories.rs:195`),
so the length guard never passes and **the branch is dead code**. Graph-only
candidates therefore enter scoring at `base_score == 0.0`, not at an inflated
cosine. The inversion comes from the graph lane instead — see R1.

## 2. Retrieval correctness (18 findings, ranked)

Final score today:

```
final = 0.3 * (decay(rrf) + Σ additive_bonuses)
      + 0.7 * (ws*rrf + wt*temporal + wc*conf + wg*graph)
      + route_boost
```

| signal | production range |
|---|---|
| fused RRF (`base_score`) | **0.016 – 0.08** |
| normalised graph score | 0 – **1.0** |
| additive bonuses | −0.43 – +0.50 |
| route boost | +0.035 – +0.138 |
| synthetic fact card | **1.0e9** |

**The retrieval signal is the smallest term by an order of magnitude.**

- **R1 (severe)** `normalize_graph_scores` divides by the per-query max, so the
  argmax is **exactly 1.0 on every query**, independent of evidence strength.
  At `weights.graph` 0.15–0.30 blended at 0.7 that is a flat **+0.21** to the
  most-connected memory, versus **~0.034** for the entire semantic contribution
  of a rank-1 dense hit — a query-independent popularity prior worth 3–6× the
  best dense evidence. Combined with C2 (graph-only candidates start at 0.0
  semantic), the inversion is ~15×. Fix: saturating `x/(x+k)` calibration, cap
  the graph weight at ≤0.10, and make graph reach reorder rather than originate.
- **R2 (high)** `select_candidates_with_session_head` round-robins across
  sessions ordered by a *different* formula, and `respond.rs` never re-sorts.
  `results[0].similarity` is frequently lower than `results[3].similarity`. Any
  rank metric computed from the returned order measures the diversity heuristic;
  any metric computed after re-sorting measures something the engine never
  returns. **Both numbers would be wrong in a paper.**
- **R3 (high)** Final count can be `limit + synthetic_facts + 2`, three of them
  carrying `similarity` of `1.0e9`, `1.0`, `1.0`. Any `recall@k` against this API
  is computed over `k+3` rows.
- **R4 (high)** On cross-encoder failure, `rerank.rs:174` substitutes all-zero
  scores; the tiebreak falls to **memory-id alphabetical order**, and that list
  is fused at weight 1.5 — the largest of any lane — while
  `diag.rerank_applied` still reports `true`.
- **R5 (high)** `rerank_stale_penalty = -0.15` is dead: `confidence_signal.max(0.0)`
  at `score.rs:197` clamps it away. The same clamp kills the negative half of
  `temporal_consistency_adjustment`. `prefers_latest` queries do not reliably
  demote superseded facts.
- **R6 (high)** `as_of` is applied in three inconsistent places. `respond.rs:193`
  injects a **present-day** fact at `final_score = 1.0e9` regardless of
  `point_in_time_ms`, so an as-of query's top result is a fact that did not hold
  then.
- **R7 (medium)** `route.memory_scores` and the entire preference lane are dead
  code; the preference lane still pays for up to 96 row lookups per query.
- **R8 (medium)** Entity matching is substring, not token (`scoring.rs:238`):
  `Sam`→"same"/"Samsung", `Jan`→"January", `Ron`→"wrong". A false match both adds
  a bonus and suppresses a penalty.
- **R9 (medium)** ~**70** free scoring parameters, not ~30; only two are
  reachable from configuration. `time_window_bonus = 0.55` is documented as a
  final-score bonus but is overwritten by `route_phase` before it reaches any score.

## 3. Storage correctness (17 findings, ranked)

Register status: **9 fixed, 2 partial, 3 open** against `REARCHITECTURE.md`.

- **S1** deletion residue — see B1.
- **S2** a failed ingest returns 500 with rows durable at `indexed=0`; the client's

  done nothing**. Only the 300 s tick repairs it.
- **S3** the repair path indexes **different text** than the happy path
  (`reindex_unindexed` skips the header-stripping and the synthetic filter), so
  the divergence is permanent. Router FTS docs are unrecoverable.
- **S4** `reindex_unindexed` can lose an update to a concurrently re-ingested
  memory (three transactions, no CAS).
- **S5** durability pragmas — see B2.
- **S6** no forward-compat guard — see B3. Also the v5 migration loads the whole
  `memories` table into RAM, on the request path for a cold tenant.
- **S7** connection cache × pool × tenants — see B4.
- **S8** `MemoryId::parse` is not round-trip stable (`"a::b::007"` → `"a::b::7"`),
  so the delete cascade's prefix match misses derived chunks — **chunks carrying
  the full text survive deletion**.
- **S9** fact-chain rebuild is O(n²); same-millisecond ties resolve
  last-writer-**loses**.
- **S10** retention/TTL never erases anything; expiry is a read-time filter only.
- **S11** tenant isolation is sound by construction (one file per tenant,
  per-tenant vector index, colliding-rowid regression test) — keep this, it is a
  paper claim.

## 4. Instrumentation

- **Six dead diagnostic fields**, `embed_ms` among them: query embedding happens
  inside the `planning` span, so `x-tm-embed-ms` is structurally zero — which is
  why every `embed` column in every run record reads 0.0.
- **Four phantom headers** the evaluator parses that the engine never emits
  (`temporal-event-hits`, `shadow-question-hits`, `facet-posting-hits`,
  `mem-scene-hits`) — four fields of hallucinated zeros in every run record.
  ~14 genuinely-measured signals are discarded at the client.
- **`bytes_per_memory` is computed and wrong**: SQLite pages only, excluding the
  HNSW index and embedding cache, and it divides a cumulative numerator by a
  per-entity denominator. It never reaches a table.
- No seed control anywhere. `RUNS=3` repeats an identical deterministic config.
- `Config` has no `Serialize`, so a result cannot be attributed to a parameter set.
- `--i-know-this-is-test` is a bare bool with no log. Splits are sealed and have
  **never been unsealed** — no run record has `split == "test"`. Keep it that way.
- `[profile.release]` sets `strip = true` **and** `debug = true`; `debug` buys
  nothing and inflates `target/` to 4 GiB.
- `/metrics` is unauthenticated, and drops every sub-millisecond query.
- Proposed: `budgets.toml` with per-tier values, `measured` vs `estimated` basis,
  and `enforce` separate from `value`; plus `check_diag_wiring.py` (pure grep,
  no build) gating dead fields and phantom headers at zero.

**The single biggest structural finding: `ComputePermits::new(max(n_embed, n_rerank))` evaluates to 1 on CPU** (`semantic.rs:524`), because both `embedding.executors` and `rerank.executors` default to 1. Every ONNX call in the process — query embedding, HyDE variants, cross-encoder rerank, and ingest embedding — serialises through **one shared semaphore slot**. This is the most likely explanation for p95 being 2.5× the mean, and widening it is zero-risk for quality.

**Two more, both zero-quality-risk:**
- `entity_pivot_sessions` runs a `LOWER(router_text) LIKE '%needle%'` full scan per subject entity **unconditionally**, not just as a backstop when FTS misses — and it runs twice per request because both `plan_phase` and `route_phase` call it.
- `register_fact_versions_*` is O(chain length) per registration: it reads the whole version chain twice and issues one UPDATE per historical row, when only the immediate neighbours change.

## 8. Distribution (round 2)

**Correction to an earlier claim of mine: `bindings/python/tellodb.py` is NOT an HTTP client.** It is a stdlib-only ctypes binding that `dlopen`s the cdylib and calls the C ABI directly (`tellodb.py:18,62-78`). I asserted otherwise several times without reading the file. The architecture is right.

**The real gap is that there is no packaging at all.** `bindings/python/` contains exactly one file — no `pyproject.toml`, no wheel, nothing on PyPI. `_find_library()` expects the user to have cloned the repo and run `cargo build --release -p tellodb-ffi`. `pip install tellodb` installs nothing because no package exists.

**FFI panic safety verified correct.** All seven exported functions route through `ffi_boundary()`, which wraps each body in `catch_unwind` and converts panics into a NULL return plus a thread-local message. With `panic = "unwind"` that is the correct pattern; nothing can unwind past `extern "C"`.

**FFI surface is a strict subset of the engine.** It exposes `open`/`ingest`/`query`/`current_fact`/`last_error`/`string_free`/`close` — but not `get_memory`, `explore_graph`, `fact_history`, `fact_as_of`, or `checkpoint`, all of which exist on `Engine` and are all exposed over MCP stdio. Every binding built on the C ABI inherits that gap. `tellodb.h` is hand-written with no `cbindgen`, so it will drift.

**Node is genuinely HTTP-only, and broken.** `node/packages/sdk` spawns a server child process and talks to it over localhost HTTP, defaulting to `https://engine.tellodb.com` unless `fromLocal()` is called. It looks for a binary named `temporal_memory` — the Rust target was renamed to `tellodb`, so the local-spawn path cannot find a freshly built binary. Its test fixtures are `.redb` files from a storage engine the project no longer uses.

**Security issue in the four published adapters.** `src/tellodb-client.js` is byte-for-byte identical across all four `@tellodb/*-memory` packages, still internally named `AletheiaMemoryClient`, reading `ALETHEIA_*` env vars — and it defaults to **`http://143.110.246.15:3000` over plaintext HTTP** with a checked-in default API key. Anyone installing an adapter without configuration ships memory data to that IP unencrypted. Worth addressing before anything else in this section.

**ARM is blocked, and for a fixable reason.** `Cargo.toml:34` sets `ort = { features = ["cuda"] }` **unconditionally** — not gated behind the crate's own `gpu-cuda` feature, which is therefore vestigial. That pulls CUDA execution-provider bindings into every build including ones targeting aarch64, where no prebuilt exists. Fixing the gating is a prerequisite for any ARM build, and ARM is what the scale-invariance claim rests on. `aarch64`/`arm64` appear nowhere in `Cargo.toml`, `src/`, `crates/` or `.github/`.

**Model packaging recommendation:** ship the 87 MiB embedder inside the wheel via the existing `bundled-models` feature; make the 1.1 GiB reranker a pinned, checksummed, opt-in first-run download (`pip install tellodb[rerank]`), with rerank defaulting **off** for the embedded path even though it defaults on for the server. Also: `bundled-models` currently covers only the embedder — there is no bundled path for the reranker at all.

## 9. Durability (round 2)

**Several storage-audit findings were fixed mid-audit and are refuted at HEAD:** the
durability pragmas, the version guard, the deletion cascade, `MemoryId` round-trip
stability, and repair-path text parity (both the happy path at `api/handlers/ingest.rs:630`
and the repair path at `storage/repo/ingest.rs:223` now call the same
`core::text::index_text_for`, with a parity test).

**What survives the re-check:**

1. **Router FTS documents are unrecoverable (CONFIRMED, medium).** `merge_router_records_tx`
   appends a router doc to the post-commit `fts_batch` keyed by an id that has **no row in
   `memories`**. A crash between the ingest commit and `fts_index_batch` loses that row, and
   `reindex_unindexed` can never find it because it scans `memories WHERE indexed = 0`. It is
   only rebuilt opportunistically if some sibling memory in the same session is still
   unindexed. Fix: write the router FTS row inside the same tx that writes `session_router`
   — the pattern already exists in `rebuild_router_after_delete`.
2. **Detached consolidation tasks have no watermark (HYPOTHESIS, high — needs a read).**
   `spawn_consolidation_tasks` is fired and not awaited (`db.rs:229-230`). Anything riding on
   it that isn't covered by the `memories.indexed` watermark has no recovery path by
   construction: the caller sees success, a kill drops the work silently.
3. **Two concrete determinism breaks — and determinism is the thesis.**
   - `fuse.rs:183-194` accumulates `graph_scores` by iterating `Vec<HashMap<String, f32>>`.
     The inner `HashMap` uses `RandomState`, so when two seeds boost the same memory the
     **f32 addition order varies run to run**, and f32 addition is not associative. Identical
     input can produce different scores in the low bits. Fix: sort contributions before
     folding, or use a `BTreeMap`.
   - `db.rs:90` generates `mem-{ts}-{rand::random::<u128>():032x}` when no id is supplied,
     which cascades into FTS rowids and edge ids. Any replay must replay recorded ids, never
     regenerate them.
   - `usearch` HNSW build determinism is **unverified** — many HNSW implementations randomise
     layer assignment. Check before claiming byte-identical vector replay.
4. **Replay is greenfield.** `grep -rn 'memory_log\|replay' src/` returns nothing. The minimum
   viable version: an append-only `memory_log` table written in the *same* transaction as
   `commit_ingest` (inheriting existing atomicity, adding no crash window), a
   `replay(policy_version, from_seq)` that re-runs `build_artifacts` into a scratch database,
   and a table-by-table diff against the live one.
5. **"One file, no sidecars" is true only of the per-tenant store.** `tenants/<id>/tellodb.db`
   plus standard WAL/SHM is genuinely one file. But `platform.db` is created unconditionally
   on every boot, `embedding_cache.sqlite` by default, and `hf-home/` + `cache/` whenever an
   explicit data dir is set — which the shipped Dockerfile does. State the claim precisely:
   *the memory of record for one tenant is one file*, and document the engine's bootstrap
   files as cache and auth state, not memory.
6. **The v5 migration is one transaction over the whole table.** It paginates 10k rows at a
   time (so not "loads everything into RAM"), but commits once at the end — a crash rolls the
   whole thing back, so a large legacy tenant retries the entire migration on every restart
   until one run completes uninterrupted.
7. **CI runs neither fuzz nor crash injection.** The two existing fuzz targets are pure
   text-parsing fuzzers that never touch SQLite. The `#[cfg(test)] FAIL_NEXT_FACT_WRITE` hook
   at `storage/repo/ingest.rs:9-10` is exactly the right shape for injection — it needs a
   `kill` variant and more sites.

**Claimable for the paper's Table 3 today, with citation:** forward-compat refusal (tested);
`synchronous=FULL` fsync-per-commit as the shipped default, so an acknowledged write survives
`kill -9`; transactional 13-table deletion cascade with a residue test.

## 10. Shrink (round 2)

**Measured, via replaying the cargo resolver over `cargo metadata` (not estimated):**

| Cut | Packages removed | Notes |
|---|---|---|
| `fastembed` default features (`image-models`) | **55** | Pulls `image` → `rav1e`, `ravif`, `exr`, `tiff`, `gif`, `zune-jpeg`, `qoi`… AV1/PNG/EXR codecs for a text-only engine |
| …plus `hf-hub` | **75 total** | Adds `reqwest`, `hyper-tls`, `hyper-rustls`, `indicatif`, `console`, `dirs`, `web-sys`. Requires `bundled-models`/`TELLODB_MODEL_DIR` instead of HF auto-download — which is the *more* batteries-included path |

One line in `Cargo.toml:33`. 418 reachable packages → ~343.

**The 26 MiB binary is ONNX Runtime.** The statically linked `libonnxruntime.a` that `ort` downloads is **70 MB** (`~/Library/Caches/ort.pyke.io/…`). It is the only large statically-linked C++ numerical library in the graph, and `__text` is 22.3 MiB of the 26 MiB binary. Nothing else is a plausible candidate.

**The reranker is a one-line fix.** `jina-reranker-v1-turbo-en` is **already a supported variant** (`semantic.rs:311`) — turbo-class rerankers are ~30–70 MB fp32 against `bge-reranker-base`'s measured **1.06 GiB**. Changing `DEFAULT_RERANK_MODEL` (`config.rs:15`) cuts the install from 1.21 GiB to ~150 MB with zero code changes, pending a quality re-benchmark.

**`[profile.release]` sets `strip = true` and `debug = true`.** `strip` wins, so `debug` buys nothing and inflates `target/release` to 4.0 GiB. One-line deletion.

**Derived-structure amplification — the real footprint story, and partly already solved.** Tracing `index_semantic` on every companion builder:

| Companion | Embedded? |
|---|---|
| chunks (`::cN`), gist, facts (`::factN`), atomic cards (`::cardN`), event | **Yes** |
| keywords (`::kw`), relations (`::relN`) | **No — already optimised out** |

**Atomic cards are the dominant volume** (~5.5 per input memory) and each gets its own encoder call and its own 384-dim stored vector — despite being, by construction, a slice of text whose *parent turn is already embedded with ±1-turn context*. Cutting card embeddings in favour of retrieving through the parent's vector is the single change that moves the 51 KB/memory number; quantization only touches ~7 KB of it. Defensible target: **~20 KB/memory**, validated by re-benchmarking after that specific change.

Also: fact dedup (`companion.rs:187`) runs *after* embedding — the duplicate is detected at cosine ≥0.94 having already paid for the encoder call. Move the decision earlier via `PredicateCanon`.

**The server split is clean.** `grep -rln "use crate::platform\|use crate::api::auth" src/query src/storage src/api/ingest` returns **nothing** — the coupling is entirely through `EngineState`'s fields (`api/mod.rs:25-37`). Splitting `platform.rs` (1,691 lines), `auth.rs` (632) and `metrics.rs` into a `tellodb-server` crate drops `argon2`, `tower-http` and `prometheus` from the embeddable core. 7.2% of source by line count, but a clean dependency cut.

**Refuted:** the shrink agent flagged a mismatch between `DEFAULT_EMBEDDING_MODEL` (`bge-small-en-v1.5`) and the local `.fastembed_cache` (which holds MiniLM), inferring the benchmarks ran against the wrong model. The run records say otherwise — `"embedding_model": "BAAI/bge-small-en-v1.5"`. The local cache is dev leftovers; benchmarks ran on the CUDA box.

**But that run record surfaces something else worth knowing:** `"device": "CUDA"`, `embed_cache_hits: 363,422` against `misses: 264`. **The 234 ms stage table is a warm-cache GPU number.** Cold-start and CPU-only latency are unmeasured, and the embedding cost that `embed_ms` fails to capture is hidden further by a 99.9% cache hit rate. Any "runs anywhere" claim needs a CPU-tier run before it means anything.
